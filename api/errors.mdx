NexCore uses standard HTTP status codes combined with machine-readable error codes in the response body. Every error response has the same envelope structure, making it straightforward to write consistent error-handling logic regardless of which endpoint you are calling.

## Error Response Format

When a request fails, the API returns a JSON body with `"ok": false` and an `error` object:

```json
{
  "ok": false,
  "error": {
    "code": "INVALID_PARAM",
    "message": "Field 'stream' is required.",
    "details": { "field": "stream" },
    "requestId": "req_01HZXXXXX"
  }
}
```

<ResponseField name="ok" type="boolean">
  Always `false` for error responses.
</ResponseField>

<ResponseField name="error.code" type="string">
  A machine-readable error code string. Use this in your application logic to branch on specific error types.
</ResponseField>

<ResponseField name="error.message" type="string">
  A human-readable description of the error suitable for logging and debugging.
</ResponseField>

<ResponseField name="error.details" type="object">
  An optional object with structured context about the error — for example, the name of the field that failed validation.
</ResponseField>

<ResponseField name="error.requestId" type="string">
  A unique identifier for this specific request. Always include this value when contacting NexCore support.
</ResponseField>

## Error Code Reference

The table below lists every error code the NexCore API can return, along with the associated HTTP status, what causes it, and the recommended action to resolve it.

| HTTP Status | Error Code | Description | Resolution |
|---|---|---|---|
| `400 Bad Request` | `INVALID_PARAM` | A required parameter is missing or the value provided is malformed (wrong type, out of range, etc.). | Check your request body against the [Endpoints reference](/api/endpoints). The `error.details` object usually identifies the offending field. |
| `401 Unauthorized` | `UNAUTHORIZED` | The `Authorization` header is missing, uses an incorrect format, or contains an expired or revoked API key. | Verify your API key in the Dashboard under **Project → Settings → API Keys**. See the [Authentication guide](/api/authentication). |
| `403 Forbidden` | `FORBIDDEN` | The API key is valid and recognized, but it does not have the permission scope required for the requested action (e.g., using a read-only key to create a resource). | Create a new API key with the appropriate scope (e.g., `write`) in the Dashboard, or use an existing key with sufficient permissions. |
| `404 Not Found` | `NOT_FOUND` | The resource you referenced — a project, stream, pipeline, or event — does not exist, or it belongs to a different project than the one your key is scoped to. | Verify the resource ID or name. Check that the API key you are using belongs to the project that owns the resource. |
| `409 Conflict` | `CONFLICT` | A resource with the same unique identifier (typically `name`) already exists in this project. | Choose a different, unique name for the new resource, or use `PATCH` to update the existing one. |
| `429 Too Many Requests` | `RATE_LIMITED` | Your project has exceeded its allowed request rate for the current window. | Implement exponential backoff and retry. See the [Rate Limits reference](/api/rate-limits) for per-plan limits and a retry code example. |
| `500 Internal Server Error` | `INTERNAL_ERROR` | An unexpected error occurred on the NexCore platform. This is not caused by your request. | Retry the request using exponential backoff. If the error persists across multiple retries, contact NexCore support and include the `requestId`. |
| `503 Service Unavailable` | `SERVICE_UNAVAILABLE` | The NexCore platform is temporarily unavailable, typically during planned maintenance or a partial outage. | Wait briefly and retry. Check [status.nexcore.io](https://status.nexcore.io) for the current platform status and any active incident updates. |

<Note>
  Check [status.nexcore.io](https://status.nexcore.io) for real-time platform health, active incidents, and historical uptime data. If you are experiencing widespread `500` or `503` errors, an active incident may already be under investigation.
</Note>

## Using `requestId` for Support

Every API response — both success and error — includes a `requestId` field in the envelope. This identifier is unique to a single request and maps directly to server-side logs on the NexCore platform.

When you contact NexCore support about an unexpected error, always include:

- The `requestId` from the error response.
- The endpoint you called (method + path).
- The timestamp of the failing request.
- A sanitized copy of your request body (remove any sensitive data before sharing).

With the `requestId`, the support team can locate the exact request in platform logs and diagnose the root cause far more quickly than without it. Store or log `requestId` values in your application wherever you surface API errors to users or operators.
